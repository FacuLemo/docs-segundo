# Clase 17, 18 y 19: Autenticación de usuarios con JWT

En estas clases vamos a ver paso por paso cómo implementar autenticación por Tokens en nuestra API, usando JWT como base.

Para eso, hay que concretar los siguientes pasos:

* Crear un modelo Usuario, y un path operation de Register donde la contraseña se guarde encriptada.
* Crear un path operation de Login, donde si las credenciales (usuario/contraseña) son correctas, devuelva un TOKEN DE ACCESO. Este token tiene una vida útil definida (duran poco).
* Finalmente, proteger nuestros path operation existentes para que exigan estar logeado si se quiere obtener el contenido. Es decir, los peticiones a esos endpoint exigen un Header de autenticación donde se mande un token de acceso válido.


De esta manera crearíamos dos nuevos módulos en nuestra app, `core/` y `api/`. En core/ tendremos la configuración del sistema de encriptación y en api/ tendremos la dependencia a inyectar en nuestros path operations para pedir que exista un usuario autenticado antes de acceder a la lógica.

### Paso 1: Configurar el Hashing de Contraseñas

Antes de la clase del token, necesitamos la herramienta para verificar las contraseñas. Usaremos `passlib`.

```python
# src/core/security.py
from datetime import datetime, timedelta, timezone
import jwt
from fastapi import HTTPException, status
from passlib.context import CryptContext
import bcrypt


def get_password_hash(password: str) -> str:
    """
    Función que a partir de una contraseña en texto plano, genera un hash.
    Convierte el str plano en bytes, genera un salt único y la 'encripta'.
    Devuelve el hash creado a partir de la contraseña. Es lo hay que guardar en la DB.
    """
    pwd_bytes = password.encode('utf-8')
    salt = bcrypt.gensalt()
    return bcrypt.hashpw(pwd_bytes, salt).decode('utf-8')

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """
    Chequea si la contraseña en texto plano coincide con la contraseña hasheada.
    No se 'des-encripta', simplemente devuelve True o False.
    """
    return bcrypt.checkpw(
        plain_password.encode('utf-8'), 
        hashed_password.encode('utf-8')
    )

```

### Paso 2: El esqueleto de `JWTManager`

Creamos la clase para encapsular la lógica, en el mismo archivo donde tenemos `get_hashed_password` (security.py). Al instanciarla, recibirá la clave secreta y el tiempo de expiración. En producción, estos valores se leerían del archivo `.env` mediante `src/core/config.py`. Por ahora, lo dejamos 'hardcodeado' cuando instanciemos la clase más abajo (paso 5). 

```python
# Continuación en src/core/security.py...

class JWTManager:
    def __init__(self, secret_key: str, algorithm: str = "HS256", expire_minutes: int = 30):
        self.secret_key = secret_key
        self.algorithm = algorithm
        self.expire_minutes = expire_minutes

```

### Paso 3: Generación del Token

Agregamos el método para crear el token. La carga útil (`payload`) necesita la fecha de expiración (`exp`) obligatoriamente para ser segura.

```python
    # Dentro de la clase JWTManager...
    
    def create_access_token(self, data: dict) -> str:
        """
        Crea un token JWT firmado.
        'data' debe contener al menos el 'sub' (subject), que suele ser el email o ID.
        """
        to_encode = data.copy()
        
        # Calculamos la fecha límite usando timezone.utc para evitar problemas de zonas horarias
        expire = datetime.now(timezone.utc) + timedelta(minutes=self.expire_minutes)
        to_encode.update({"exp": expire})
        
        # jwt.encode empaqueta el header, el payload y firma el token
        encoded_jwt = jwt.encode(to_encode, self.secret_key, algorithm=self.algorithm)
        
        return encoded_jwt

```

### Paso 4: Validación y Manejo de Errores

Este es el método que leerá cada petición entrante para ver si el token es válido. Es fundamental capturar las excepciones específicas de `PyJWT` para darle al cliente (o al frontend) una respuesta HTTP clara.

```python
    # Dentro de la clase JWTManager...

    def verify_token(self, token: str) -> dict:
        """
        Decodifica el token. Si algo falla, interrumpe la petición con un error HTTP 401.
        """
        try:
            # jwt.decode verifica automáticamente la firma y la fecha de expiración ('exp')
            payload = jwt.decode(token, self.secret_key, algorithms=[self.algorithm])
            return payload
            
        except jwt.ExpiredSignatureError:
            # El token es real, pero ya caducó
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="El token ha expirado",
                headers={"WWW-Authenticate": "Bearer"},
            )
        except jwt.InvalidTokenError:
            # El token fue alterado, está mal formado o firmado con otra clave
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Token inválido",
                headers={"WWW-Authenticate": "Bearer"},
            )

```

### Paso 6: El "Puente" de Dependencias (`src/api/deps.py`)

Este archivo centraliza las inyecciones de dependencias. Aquí le decimos a FastAPI cómo extraer el token de la petición HTTP y cómo validarlo contra un usuario real de la base de datos.

```python
# src/api/deps.py
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from sqlmodel import Session, select

# Importamos las herramientas que ya construimos
from src.database import get_session  # La función que devuelve la sesión de la BD
from src.core.security import jwt_manager
from src.models.users import User     # modelo Usuario

# OAuth2PasswordBearer le dice a FastAPI (y a Swagger UI) dónde está el endpoint de login.
# Extraerá el token del header "Authorization: Bearer <token>"
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="auth/login")

def get_current_user(
    token: str = Depends(oauth2_scheme), 
    session: Session = Depends(get_session)
) -> User:
    """
    Dependencia central. Valida el token y devuelve el usuario de la BD.
    Se inyectará con Depends() en cualquier ruta que queramos proteger.
    """
    # 1. Usamos nuestro manager para decodificar (lanza error si expiró o es inválido)
    payload = jwt_manager.verify_token(token)
    
    # 2. Extraemos el 'sub' (email o ID) que guardamos al crear el token
    user_email: str = payload.get("sub")
    if user_email is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED, 
            detail="Credenciales inválidas"
        )
        
    # 3. Buscamos al usuario en la base de datos con SQLModel
    statement = select(User).where(User.email == user_email)
    user = session.exec(statement).first()
    
    if not user:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND, 
            detail="Usuario no encontrado"
        )
        
    # Retornamos el objeto User completo de SQLModel
    return user

```

### Paso 7: El Endpoint de Login (`src/routers/auth.py`)

Finalmente, creamos la puerta de entrada. En este archivo consumimos el `verify_password` y el `create_access_token` que programamos en el paso 1 y 3.

```python
# src/routers/auth.py
from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm
from sqlmodel import Session, select

from src.database import get_session
from src.models.users import User
from src.core.security import verify_password, jwt_manager

router = APIRouter(prefix="/auth", tags=["Autenticación"])

@router.post("/login")
def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    session: Session = Depends(get_session)
):
    """
    Recibe las credenciales, las verifica y devuelve el JWT.
    """
    # 1. Buscar al usuario por el username (en este caso, usamos el email)
    statement = select(User).where(User.email == form_data.username)
    user = session.exec(statement).first()
    
    # 2. Verificar que exista el usuario
    if user is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Correo o contraseña incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )
    # y contraseña (usamos verify_password de security.py)
    if not verify_password(form_data.password, user.hashed_password):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Correo o contraseña incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )
    
    # 3. Generar el token
    access_token = jwt_manager.create_access_token(data={"sub": user.email})
    
    # 4. Retornar en el formato estándar de OAuth2
    return {
        "access_token": access_token,
        "token_type": "bearer"
    }

```

### El resultado final en la práctica

Con esta estructura, cuando quieras proteger cualquiera de tus rutas (por ejemplo, en `src/routers/juegos.py`), el código queda extremadamente limpio porque toda la lógica pesada está abstraída:

```python
# src/routers/juegos.py
from fastapi import APIRouter, Depends
from src.models.users import User
from src.api.deps import get_current_user # importamos

router = APIRouter(prefix="/juegos", tags=["Juegos"])

@router.post("/")
def crear_juego(
    # ... tus datos de entrada ...,
    current_user: User = Depends(get_current_user) # Protección de la ruta, a través del Token
):
    return {"mensaje": f"Juego creado por {current_user.email}"} #Y podemos acceder al usuario.

```

De esta manera entendemos cómo las apis protegen las sesiones de los usuarios. Y modularizado de esta manera, podemos ver cómo una aplicación del mundo real aísla sus responsabilidades: la base de datos se encarga de los datos, `core` de la encriptación, y `api/deps` hace de puente entre todas las funciones.

El flujo nos quedaría de la siguiente manera:

* Un cliente se registra a través de `/register` con un usuario y contraseña en texto plano. El servidor recibe la petición, encripta la contraseña, y se guarda en la db.
* El cliente le pega a `/login` de nuevo con usuario y contraseña. El servidor hace un verify_password con los datos que se enviaron, y si coincide, devuelve como respuesta un token de acceso. El cliente debe guardarse ese token.
* El cliente, ahora con el token, puede pegarle a `/articulos` y enviar el token obtenido a través del header de Bearer Token (en esa misma petición). Cuando le llega al servidor, se lee el token y si no está expirado, devuelve como respuesta los articulos. Si se enviase una petición a artículos sin token, directante se rechaza y el servidor devuelve un 401.
